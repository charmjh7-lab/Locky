# 작업 범위·기존 디자인 보존 및 요구사항의 근거 (최우선 운영 규칙)

이 문서는 제품·UX·UI·접근성·CI 가이드의 적용 범위를 제한하는 상위 작업 규칙이다. 특정 사용자 요청에 의해 변경이 승인되지 않은 화면·동작·데이터는 개선 대상으로 간주하지 않는다. 설계 품질을 높이라는 일반 원칙은 무관한 변경을 허가하지 않는다.

## 권한과 해석의 우선순위

현재 작업에 대한 사용자의 구체적 요청 및 명시적인 금지·유지 조건, 사용자가 이전에 승인한 제품 결정, 현재 작동하는 코드·사용자 데이터와 호환성 계약, 제품별 문서, 일반 UX/UI/개발 권고의 순서로 해당 범위에서 판단한다. 보안·개인정보·법령·플랫폼의 필수 제약을 침해하는 구현은 피하고 충돌을 알린다. 서로 모순되는 문서가 있다면 임의로 가장 편한 규칙을 선택하지 않고 실제 요청과 변경 이력으로 근거를 확인한다. 신규 프로젝트의 미결정 사항은 승인된 요구사항처럼 취급하지 않는다.

## 명시적 변경 요청 없이는 유지

기존 UI의 구조·배치·정렬·크기·높이·간격·여백·고정/스크롤 영역·색상·텍스트·내비게이션·사용 흐름·버튼 실행 방식을 기본적으로 보존한다. '사용성을 고려', '시각적 위계를 개선', 'AI 슬롭을 피함', '여백을 정리' 등의 일반 규칙은 자동 UI 개편 지시가 아니다. 특정 버그를 고치거나 지정 기능을 구현하는 데 필수적인 국소 변화만 허용하며, 원래 조작과 주변 화면이 영향을 받는지 확인한다. 명시적으로 UI 재설계가 요청되었다면 그 승인 범위 안에서만 창의적인 설계 판단을 한다.

작업 중 그 밖의 UX 문제가 보이면 코드나 테스트의 기대값을 몰래 변경하지 않는다. '추가 제안(미적용)'으로 따로 보고하고 사용자의 승인을 기다린다. 단순한 예방적 디자인 수정도 범위 밖이라면 제안만 한다. 버그 수정에 필수적인 연관 변경은 이유·영향·검증을 설명한다.

## 요구사항 문서의 출처 관리: 스스로 만든 가정을 공식 요구사항으로 바꾸지 않는다

`docs/PRODUCT_PRINCIPLES.md`, `docs/UX_PROJECT_BRIEF.md`, ADR, 화면 설계·테스트 계약 등 제품 의도를 설명하는 문서는 현재 구현·개발 모델의 선호만으로 새로운 확정 요구사항을 추가하는 곳이 아니다. 예컨대 '목적 영역을 중앙 정렬하는 편이 좋겠다'는 모델의 아이디어를 기존 디자인에 대한 사용자 승인으로 기록해서는 안 된다.

문서의 내용은 확인된 사용자 결정 / 현재 구현에서 관찰한 사실 / AI의 제안(미승인) / 미결정을 구별한다. 변경 작업과 관련된 요구사항 문서는 실제 요청·승인·변경된 인터페이스 사실을 정확히 기록하는 경우에만 업데이트한다. 기존 UI를 먼저 임의 변경한 뒤 이를 근거로 제품 원칙을 소급 변경하는 것은 금지한다. 사용자 승인 여부가 불명확하면 확정으로 적지 않고 제안으로 남기거나 필요한 질문을 한다. 코드·테스트·설계 문서를 동시에 바꾸어 변경을 정당화하는 순환 논리를 만들지 않는다.

## 변경 전후의 간단한 범위 게이트

변경 전에 이번에 요청된 동작과 변경하지 말아야 할 기존 동작·화면 영역을 내부적으로 정한다. 변경한 파일과 화면이 요청과 직접 관련되는지 확인한다. 새 UI 테스트나 스냅샷은 사용자가 승인하지 않은 레이아웃을 '정답'으로 고정하지 않게 하고, 변경 전 동작과 사용자 계약을 기준으로 검증한다. 추가로 바꾸고 싶은 사항은 구현하지 않은 제안으로 보고한다. 작은 변경에는 긴 보고서나 추가 회의를 강제하지 않지만, 범위가 불명확한 큰 레이아웃 변경에는 먼저 사용자 확인을 구한다.

## 완료 보고

요청된 변경, 이에 필수적으로 따른 변화, 기존 UI·동작 보존 여부, 실행 검증과 미확인 사항을 구별한다. 이 규칙 위반으로 인한 범위 밖 변경을 발견했다면 숨기지 않고 영향과 원복 필요성을 보고한다. 문서를 수정했다고 실제 앱의 기능이 수정된 것은 아니다.
