# 인터랙션 완결성 계약: 버튼 존재가 아니라 작업 완료까지

## 개발 시작 전 ‘사용자 작업’으로 기능을 정의한다

화면과 데이터를 확인하여 사용자가 다루는 객체와 목적을 파악한다. 일시적인 버튼 목록이 아니라 사용자에게 의미 있는 행위 단위로 기술한다. 예를 들어 노트에서는 생성, 열기, 편집, 저장, 복사, 이동/정렬, 삭제/복구가 필요한지 각각 판단한다. 앱의 목적과 무관한 조작을 무조건 추가하지 않는다. 목록에서 항목을 열 수 있어도 수정·삭제가 불가능하면 사용자 작업은 완결되지 않을 수 있다.

UI 설계 시 각 주요 객체에 아래 '작업 계약'을 최소한 내부적으로 적용한다. 전체 문서화는 핵심 화면·상태를 새로 만들거나 반복 장애를 겪는 경우에 집중한다.

| 작업 계약 | 확인 내용 |
|---|---|
| 진입 | 사용자가 어디서 기능을 발견하고 대상 객체를 선택하는가? |
| 권한·제약 | 가능한 상태와 비활성 상태, 누를 수 없는 이유가 이해되는가? |
| 실행 | 실제 callback·navigation·repository·서버/모델 호출이 의도한 대상을 가리키는가? |
| 피드백 | 눌림·진행·실패·성공·되돌림이 보이는가? 장애가 날 때 멈춰 있는 것처럼 보이지 않는가? |
| 결과 | 데이터/현재 화면/다른 화면/나중에 재진입 시 예상한 내용이 그대로 반영되는가? |
| 취소·복귀 | 실행 전 취소, 작업 중 중단, 시스템 뒤로, 계층적 닫기가 일관되는가? |
| 실패·반복 | 연타, 느린 저장, 빈 값, 권한 거부, 중복 요청, 부분 실패에서 손상·중복이 없는가? |

## 버튼의 실제 동작을 검증한다

디자인만 존재하고 onClick이 없거나, handler는 실행하지만 잘못된 항목 ID를 수정하거나, 상태만 메모리에서 변경해 화면 재진입 때 원복되는 결함을 금지한다. 비동기 동작은 중복 입력 방지와 완료·실패 신호를 연결한다. 삭제 후 목록 개수·선택·뒤로/복구와 영속 데이터를 확인한다. 편집 입력값의 저장·취소가 실제로 다른 결과를 갖게 한다. 제어가 disabled 상태라면 이유나 적절한 다음 행동을 제공한다.

상태 변경의 트랜잭션 경계를 명확히 한다. 손을 뗐을 때 확정되는 드래그·크기 변경, 입력 중 미리보기, 저장 대기, 앱 종료 후 복원 간 차이를 검증한다. 테스트가 내부 함수만 확인했다면 실제 UI 경로를 확인했다고 표현하지 않는다.

## 대화상자·바텀시트·팝업의 닫기와 주요 작업

사용자가 내용을 보거나 편집하는 창에는 화면 목적에 맞는 취소·닫기·저장/확인과, 필요한 경우 삭제·수정 경로가 있어야 한다. 긴 콘텐츠가 스크롤돼도 필수 행동이 찾기 어려운 맨 아래로 밀려나지 않도록 한다. 일반적으로 독립적인 스크롤 본문과 고정된 action/footer를 고려하되 작은 높이, 키보드, edge-to-edge insets, 큰 글꼴을 함께 고려한다. 고정 헤더·푸터가 내용을 가리게 해서도 안 된다. 닫기 X 하나만 제공하는 방식이 적합한지, 시스템 뒤로·외부 터치·Escape 동작은 어떤지 제품 상황에 맞게 결정한다.

중첩 모달·하위 편집 화면을 닫으면 이전 부모 창과 스크롤 위치·선택 상태로 돌아간다. 주요 저장/취소 버튼에 닿기 위해 지나치게 긴 설명을 읽어야 하거나 키보드를 수동으로 닫고 스크롤해야 하는 흐름은 재설계한다. 사용자 확인이 필요한 고위험 삭제에는 사전 확인이나 Undo/휴지통 같은 적절한 복구 수단을 둔다. 그러나 일반적인 보기·탐색에 매번 확인 대화상자를 붙이지 않는다.

## 사용자 객체의 맥락을 유지한다

목록의 대상 메뉴는 필요한 경우 대상 주변에 두고, 화면 정중앙·반대쪽에 나타나 손과 시선이 멀리 이동하지 않게 한다. 멀티선택은 선택/해제/전체 선택/일괄 작업/삭제/취소 의미를 구별한다. 현재 위치 표시와 ‘선택됨’ 표시는 다른 상태이므로 같은 색·모양으로 혼동시키지 않는다. 제스처·길게 누르기만으로 필수 기능을 감추지 말고 보조 접근 경로를 검토한다.

## 제품별 적용 범위를 정한다

읽기 앱에서는 저장/삭제보다 위치 탐색·모드 전환·재생 제어가 핵심일 수 있고, 필기 앱에서는 손가락/펜 입력과 Undo가 핵심이다. 학습 앱에서는 노트·경로·카드의 관리와 대화 연속성이 중요하다. **전 기능 일괄 CRUD를 강제하지 않되, 제공하는 객체의 생애주기와 주요 행동에 빠진 고리가 없는지 확인한다.**
