# 의도 있는 UI·시각적 위계·디자인 완성도 지침

이 문서는 AI가 화면을 기능 목록이나 비슷한 카드의 반복으로 구성하는 관성을 방지하기 위한 작업 기준이다. 목표는 특정 유행 스타일을 복제하는 것이 아니라 **제품 목적에 맞는 시각적 언어, 한눈에 드러나는 행동 우선순위, 정돈된 밀도와 일관된 조작감**이다. 이 문서만 읽고 기존 앱의 디자인 시스템을 새로 교체하지 않는다.

## 1. 화면의 주인공을 먼저 결정한다

한 화면의 1차 목적을 문장 하나로 기술하고 사용자에게 가장 중요한 행동 또는 정보가 시각적으로 자연스럽게 먼저 인식되도록 한다. 1차 요소와 2차 도구·메타데이터·설정을 모두 같은 크기의 버튼이나 카드로 표현하지 않는다. 강조는 크기, 글꼴 굵기, 대비, 공간, 위치, 배경 등 여러 수단 중 맥락에 맞는 소수만 활용한다. 모든 것을 강조하면 아무것도 강조되지 않는다.

동일 화면에서 사용자에게 여러 선택권이 동등하게 중요할 때는 하나의 무리한 '정답 버튼'을 만들어서는 안 된다. 중요도는 사업적 우선순위가 아니라 사용자 의도와 실제 상황을 기준으로 판단한다. 제품이 행동의 중단을 의도적으로 지원한다면 취소·나가기 역시 정당한 1차 선택이 될 수 있다.

## 2. 공간·레이아웃: 빈 공간을 무작정 채우지 않는다

여백은 관계를 나누고 주의를 모으기 위한 자원이다. 빈 공간이 많다고 모든 카드나 편집기를 화면 높이에 맞게 무제한 확장하지 않는다. 콘텐츠에 적합한 크기를 유지하면서 상하 균형, 그룹 간 거리, 고정된 핵심 행동, 시선 이동과 손가락 동선을 함께 검토한다.

보조 도구와 주된 행동이 별도 의미 집합이라면 영역을 구분한다. 다만 테두리·그림자·여러 겹 카드로 '완전 분리'를 과시하기보다 배경의 미묘한 차이, 간격, 제목·아이콘·배치의 질서로 관계를 표현한다. 목적 선택이 하단에서 더 편한 특정 앱이 있더라도 모든 신규 앱에 이를 강제하지 않는다.

작은 화면에서 핵심 선택을 보기 위해 의미 없는 스크롤을 요구하는지 확인한다. 동시에 '무조건 무스크롤'을 규칙으로 삼지 않는다. 중요한 것은 기본 행동을 발견할 수 있고 화면이 좁아졌을 때 정보와 조작이 자연스럽게 이동하는 것이다.

## 3. 반복 컴포넌트와 색의 의미

| 요소 | 우선 판단 기준 | 피해야 할 기본값 |
|---|---|---|
| 카드·패널 | 콘텐츠 그룹이나 조작 단위가 명확할 때 사용 | 모든 텍스트를 둥근 카드로 감싸기 |
| 버튼 | 주요/보조/위험/취소의 역할과 가시성 | 모든 버튼을 동일 색·크기·강조로 표현 |
| 아이콘 | 익숙한 의미, 함께 표시할 레이블, 실제 기능 일치 | 장식용 이모지·의미 불명 아이콘 남용 |
| 색상 | 상태·강조·브랜드를 일관되게 표시 | 무작위 그라데이션·자주색/파랑색 'AI 룩' 기본 적용 |
| 그래프·배지 | 수치 비교·위험 상태·추세를 이해하기 쉽게 할 때 | 실질 정보가 없는데도 대시보드처럼 꾸미기 |
| 애니메이션 | 변화의 원인·방향·완료를 알리는 피드백 | 집중 방해·지속 반복·느린 장식 연출 |
| 구분선·그림자 | 위계 구분에 실제 도움이 될 때 | 과도한 중첩·복잡한 테두리 |

디자인 토큰(간격, 타이포그래피 크기, 색, 반경, elevation 등)은 앱 기술 스택에 맞는 한 곳에서 관리한다. 기존 토큰이 있으면 그것을 우선 활용하고, 간격·색의 임의값을 화면마다 중복해서 생성하지 않는다. 숫자 자체는 실제 디바이스와 제품 맥락을 확인한 뒤 결정한다.

## 4. 문장과 마이크로카피: AI 특유의 상투성을 없앤다

화면 문구는 '무슨 상태인가', '무엇을 하면 되는가', '어떤 결과가 생기는가'에 답해야 한다. 모든 화면에 감성적인 헤드라인·격려 문구·상투적인 부제·불필요한 인사말을 붙이지 않는다. 감성적 문구가 제품의 경험에 도움이 되는 시점에는 허용하되, 위치와 반복 빈도를 절제한다. 실패 메시지는 막연한 '문제가 발생했습니다'보다 사용자가 취할 수 있는 다음 행동과 상태 보존 여부를 알려야 한다.

원시 Markdown 기호, 개발자용 상태명, 지나치게 긴 출처 URL, 디버그 정보 등이 사용자 본문에 그대로 드러나지 않도록 한다. 원문·출처를 확인할 권리는 유지하면서 필요한 경우 접고 펼치는 등 맥락에 맞게 표현한다. 법적 안내·필수 조건·의미를 바꾸는 요약은 숨기지 않는다.

## 5. 터치·입력·내비게이션은 시각 설계와 함께 결정한다

버튼의 배치가 예쁘더라도 누르기 어렵거나 키보드에 가려지면 실패다. 실제 기기에서 눌림 영역, 인접 요소 간 간섭, 손가락으로 접근하기 쉬운 위치를 살핀다. 포커스 이동, Enter 동작, 하드웨어 뒤로가기, 대화상자 바깥 터치, 스크롤 중 고정 버튼, 중복 탭, 긴 누르기와 짧은 누르기의 발견 가능성을 포함한다.

작업을 끝내지 않고 다른 앱으로 이동하는 사용자가 많다면 최근 앱 목록에서의 복귀, 화면 회전, 폴더블 펼침·접기, 프로세스 재생성, 권한 화면에서의 복귀를 관련 테스트에 넣는다. 입력 중인 텍스트·선택한 항목·스크롤 위치가 사라지지 않아야 할 경우 앱의 상태 소유자를 명확히 한다.

## 6. 반응형·접근성·테마

라이트·다크 모드 모두에서 충분한 대비와 읽기 쉬운 타이포그래피를 확보한다. 동적 글꼴 확대, 스크린리더 레이블, 키보드·포커스 이동, 색만으로 정보를 전달하지 않는 상태 표현을 검토한다. Android면 시스템 바·디스플레이 컷아웃·IME inset·안전 영역·폴더블 윈도우 크기 변화를, 웹이면 실제 뷰포트와 브라우저 확대를 고려한다.

평균적인 화면 캡처 한 장만으로 전체 레이아웃을 완성했다고 판단하지 않는다. 제품에 실제 영향을 주는 최소/일반/넓은 화면 및 빈 데이터·긴 데이터 등의 상태를 확인한다. 모든 제품에서 수십 개의 해상도 테스트를 강제하지는 않는다.

## 7. 미완성 화면과 AI 슬롭을 구별하는 검토

다음 질문에 실제 앱 기준으로 답할 수 있어야 한다. 처음 방문한 사용자는 제일 중요한 행동을 곧바로 찾을 수 있는가? 모든 요소가 같은 강도로 떠 있지는 않은가? 도구와 본 기능의 관계를 알 수 있는가? 텍스트가 기능 설명보다 장식에 치우쳐 있지는 않은가? 여백이 의도적으로 배치되었는가? 작고 긴 화면, 입력 중 화면, 실패 후 화면에서도 조작이 가능한가? 수치와 출처가 꾸며낸 것처럼 보이지 않고 근거에 맞게 표현되는가?

문제가 발견되면 카드 추가·색 변경만 반복하지 말고 화면의 목적, 정보 우선순위, 사용자 동선으로 돌아가 필요한 범위에서 수정한다. 단, 기존 디자인의 일관성을 이유 없이 깨뜨리지 않는다.

## 8. 구현과 검증의 효율

UI 작업이 경미하면 실제 화면 코드만 수정하고 관련 검증으로 마친다. 큰 화면 개편이라면 기존 뷰와 상호작용을 파악한 뒤 핵심 화면의 구조·타이포그래피·공간 체계를 먼저 확정하고 연관 화면에 확장한다. 실제 앱과 어긋나는 별도 HTML 시안을 의무적으로 만들지 않는다. 필요할 때에만 실제 앱 프레임워크 기반 프로토타입이나 스크린샷 비교를 활용한다.

UI 수정의 성공 판정은 시각적 인상만이 아니라 이전과 동일하게 기능이 작동하는지, 접근성·입력·복귀·화면 변화가 깨지지 않는지를 포함한다. 고비용 에뮬레이터·전체 빌드는 수정 위험과 최종 배포 필요성을 기준으로 선택한다.

## 실제 버튼 배치·테마·상태 검증

시각적 위계만 조정하고 실제 사용자 작업을 잊지 않는다. 레이아웃 변경 시 주요 버튼(확인/저장/닫기/취소/편집/삭제 등 **제품 맥락에 필요한 것**)의 존재 여부, 터치 가능 영역, 시각적 강조, 실제 수행 결과와 오류 상태를 함께 검토한다. 긴 다이얼로그는 콘텐츠 스크롤과 action 영역이 함께 밀리지 않도록 설계하고, 키보드·안전 영역·작은 화면에서 조작을 가리지 않는다. 중요한 조작을 숨은 제스처 하나에만 의존하게 만들지 않는다.

모든 사용 화면의 밝음·어두움 모드에서 텍스트/아이콘/카드 경계/선택/비활성/에러/포커스 등의 대비를 점검한다. 일반 안드로이드 터치 대상 48dp 가이드와 웹 접근성의 기준을 구분한다. 기기별 화면 크기는 실제 가용 창 크기와 인셋을 반영한다. 공식 근거는 `EXTERNAL_STANDARDS.md`, 작업 종료 시나리오는 `HUMAN_UX_ACCEPTANCE.md`를 참조한다.
