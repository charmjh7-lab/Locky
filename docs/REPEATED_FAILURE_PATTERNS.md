# 반복적으로 발생한 개발·UX 실패 사례와 대응 계약

이 문서는 여러 앱의 실제 개발 요청에서 반복된 실패 **유형**을 식별해, 새 프로젝트 개발 에이전트가 같은 실수를 되풀이하지 않도록 하는 기준이다. 기능을 새 프로젝트에 그대로 이식하라는 요구가 아니다. 기존 제품 원칙과 사용자 요청을 우선하고 아래의 일반화된 실패 조건을 현재 기능에 맞춰 적용한다. 과거 보고에 ‘수정 완료’라고 적혀 있어도 이 문서에서는 실제 성공이 입증된 것으로 취급하지 않는다.

## 확인 근거의 성격

사용자가 과거 개발 대화에서 보고한 현상, 실제 사용 중 불편과 반복 수정 요청을 중심으로 정리하였다. 앱별 구체적 언급은 사용자의 문제 제기 사례이며 모든 버전에서 현재도 재현된다는 뜻은 아니다. 외부 Google·W3C·NN/g 문서는 별도의 `EXTERNAL_STANDARDS.md`로 구분하여, 사용자 경험상의 기준과 공식 플랫폼 기준을 혼동하지 않는다.

## 반복 패턴에서 얻는 설계 판단

‘삭제 버튼을 반드시 모든 화면에 추가하라’가 아니라 **사용자가 생성·수정·정리할 수 있는 객체라면 삭제·복구·편집 등의 작업이 제품 의도와 맞게 완결되어야 한다**는 원칙이다. 삭제가 허용되지 않는 기록이나 되돌릴 수 없는 법적 자료 등에는 적절한 대안·이유를 제공한다. 또한 ‘모든 모달을 같은 위치에 만들라’가 아니라 **필수 행동이 스크롤·키보드·안전 영역 때문에 가려지지 않는지 확인하라**는 원칙이다.

중요도에 따라 작업 범위를 결정한다. 작은 버그에는 관련 버튼의 실제 동작·저장·복귀만 확인하면 되고, 핵심 화면 개편에서는 콘텐츠 작업 목록과 전체 행동 흐름, 반응형·테마를 함께 검토한다. 과도한 테스트·시안 생성은 별도 품질 문제이며 변경 위험과 이전 검증 결과를 반영한다.
