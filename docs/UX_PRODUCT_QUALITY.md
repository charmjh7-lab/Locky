# 사람 중심 제품 경험·사용성 품질 규칙

이 문서는 코딩 에이전트가 기능을 구현했다는 사실과 사용자가 실제로 목적을 달성할 수 있다는 사실을 혼동하지 않도록 하는 상시 개발 지침이다. 화면이 예쁘게 보이는 것만으로 UX가 완성되지는 않는다. `PRODUCT_PRINCIPLES.md`는 제품의 목적과 지켜야 할 계약을 정하고, `UX_PROJECT_BRIEF.md`는 이 앱에서의 이용 상황과 우선 경험을 구체화하며, `UI_DESIGN_GUIDE.md`는 시각·정보·상호작용 표현을 다룬다. 이 문서들은 서로 대체재가 아니다.

여기서 언급하는 사례는 원칙을 설명하기 위한 것이다. 특정 앱의 위치·문구·색·버튼·지연 시간을 새 프로젝트에 그대로 강제하지 않는다. 기존 기능과 제품 철학을 우선하고, 사용자의 명시적 요청과 실제 구현에 맞추어 판단한다.

## 1. 구현 전에 사람의 행동을 이해한다

화면·기능을 설계할 때는 먼저 사용자가 무엇을 하려는지, 어떤 상황에서 사용하는지, 진입 시 어떤 정보를 이미 알고 있는지, 끝났을 때 성공을 어떻게 인식하는지 확인한다. 기능 목록을 그대로 세로 배치한 화면이나 내부 데이터 구조를 사용자 메뉴로 옮긴 화면을 기본 해법으로 삼지 않는다.

최소한의 행동 흐름을 실제 동사로 생각한다. 예를 들어 `열기 → 현재 상태 이해 → 주된 선택 → 결과 확인 → 이어하기/되돌리기/종료`처럼 출발점부터 종료까지 따라간다. 작업 중간의 상태뿐 아니라 앱 첫 실행, 재방문, 요청 실패, 중단 후 재개까지 고려한다. 새로운 프로젝트라면 `UX_PROJECT_BRIEF.md`의 핵심 시나리오를 채우거나 사용자 요청에서 확인 가능한 내용을 반영한다. 모든 사소한 변경에 별도 리서치·설계 보고서를 만드는 것은 요구하지 않는다.

| 확인 관점 | 사람 기준으로 답해야 할 질문 | 자주 생기는 실패 |
|---|---|---|
| 목적 | 이 화면에서 사용자가 가장 먼저 하고 싶은 것은 무엇인가? | 개발자가 제공하는 모든 기능을 동일한 비중으로 노출 |
| 발견 | 처음 보는 사람이 다음 행동을 설명 없이 찾을 수 있는가? | 핵심 선택이 일반 텍스트·장식 속에 묻힘 |
| 노력 | 목적 달성까지 필요한 탭·입력·판단·스크롤이 적절한가? | 불필요한 확인과 설정 단계 증가 |
| 피드백 | 눌렀을 때 진행 중·완료·실패를 명확히 알 수 있는가? | 클릭 후 무반응, 중복 전송·중복 저장 |
| 통제 | 취소·뒤로가기·나중에 하기·복귀가 가능한가? | 사용자를 특정 행동으로 몰아감 |
| 지속 | 앱을 떠났다가 돌아와도 같은 작업을 이어갈 수 있는가? | 새 화면으로 초기화·초안 손실·중복 호출 |

## 2. '의도적인 마찰'과 '불필요한 방해'를 구분한다

이용 시간을 줄이거나 주의를 환기하는 앱에서는 짧은 기다림·자기 선택을 유도하는 단계가 제품 기능일 수 있다. 반면 기록, 독서, 학습, 메시지 작성 등 핵심 생산 행동에 의미 없는 지연을 추가하는 것은 사용성을 해친다. 모든 화면을 무조건 클릭 수 최소화로 최적화하거나, 반대로 모든 행동에 확인 창을 붙이지 않는다. 지연·제약이 필요한 경우 그 행동의 목적과 효과, 사용자가 가질 취소·중단 권한을 문서화한다. 특정 앱에서의 '그냥 끄기'나 최하단 버튼 배치를 새 앱의 보편 규칙으로 만들지 않는다.

사용자에게 중요하거나 돌이킬 수 없는 삭제·전송·결제·공개·권한 변경에는 적합한 확인과 복구를 마련한다. 일상적 탐색이나 되돌릴 수 있는 조작에는 과도한 확인창·모달을 넣지 않는다. 사용자의 주의를 지켜야 한다는 이유로 선택권을 숨기거나 죄책감을 유발하는 문구를 사용하지 않는다.

## 3. 화면을 상태 전이로 설계한다

정상 화면 하나만 보고 끝내지 않는다. 최소한 진입·로딩·결과 표시·빈 결과·오류·재시도·취소·다른 화면 이동·복귀를 고려한다. 해당 기능에 없는 상태를 억지로 만들 필요는 없으나, 존재하는 비동기·영속 상태를 누락하지 않는다. 터치가 실제로 처리되었는지, 중복 입력이 가능한지, 화면 뒤로갔을 때 요청과 데이터가 어떻게 되는지 확인한다.

| 현실 상황 | 기대 동작 |
|---|---|
| 첫 이용·권한 미허용 | 왜 권한이 필요한지 짧게 설명하고 가능한 기능과 불가능한 기능을 구분한다 |
| 데이터 0건·필터 결과 없음 | 빈 화면을 오류처럼 보이게 하지 않고 다음 행동을 안내한다 |
| 느린 요청·오프라인 | 기다림을 확인할 수 있고 실패·취소·재시도 시 중복 결과가 생기지 않는다 |
| 긴 제목·많은 데이터·다국어 | 정보가 잘리지 않거나, 줄바꿈·펼치기·스크롤의 의미가 일관된다 |
| 키보드·큰 글꼴·작은 화면 | 핵심 작업 버튼, 입력 위치, 오류 메시지에 접근할 수 있다 |
| 화면 회전·폴더블·백그라운드·최근 앱 복귀 | 저장된 작업·초안·현재 위치와 사용자 의도가 보존된다 |
| 기능 일부 실패 | 정상인 본문과 사용 가능한 기능을 함께 폐기하지 않는다 |
| 예상 밖의 실제 데이터 | 테스트용 완벽한 데이터에만 맞춘 화면·상태 처리를 피한다 |

## 4. 정보 설계: 한눈에 이해하고 필요할 때 파고들 수 있어야 한다

사용자가 의사결정을 내리는 화면에서는 먼저 결과·핵심 행동·주의가 필요한 정보가 보여야 한다. 세부 기록, 부가 통계, 원문 출처, 긴 설명은 필요할 때 펼쳐서 볼 수 있게 한다. 다만 중요한 경고·필수 조건을 접어 감춰서는 안 된다. 분석·브리핑처럼 정보가 많은 화면에서는 앱이 사실·수치·시각적 구조를 책임지고, AI가 작성한 설명은 부가적인 해석으로 분리하는 편이 안전하다. 모델이 매번 임의의 UI 구조를 만들어 시각적 일관성을 깨뜨리지 않게 한다.

'깔끔하게' 또는 '요약해서'라는 추상적 지시만으로 핵심 데이터가 소실되지 않도록 한다. 사용자가 더 자세히 확인해야 할 이유와 원문 접근 경로가 살아 있는지 확인한다. 카드는 콘텐츠의 유형·관계가 실제로 구분될 때만 사용하고, 모든 항목을 독립 카드·그래프·배지로 꾸미지 않는다.

## 5. 작업 과정과 완료 판정

사소한 버그, 문구 수정, 국소 배치 조정은 관련 화면과 기존 설계를 확인한 뒤 바로 수정할 수 있다. 화면 구조나 상호작용을 크게 바꾸는 작업은 먼저 실제 이용 흐름과 정보 우선순위, 변경이 영향을 줄 다른 화면을 검토한다. 필요하면 구현 전 사용자에게 서로 다른 방향을 비교해서 제시하되, 매번 시안 세 개·목업·프레젠테이션을 만드는 절차를 강제하지 않는다.

| 단계 | 실제로 수행할 일 | 남겨야 할 최소 근거 |
|---|---|---|
| 현황 확인 | 기존 화면/코드, 진입 경로, 제품 원칙, 실패 사례를 확인 | 무엇을 유지하고 무엇을 개선할지 |
| 경험 정의 | 사용자의 주된 행동과 전·후 상태, 예외·취소·복귀를 설명 | 핵심 시나리오와 성공 조건 |
| 정보·시각 설계 | 강조할 행동, 보조 기능, 화면 밀도·그룹·피드백 판단 | 임의 배치가 아닌 이유 |
| 실제 구현 | 기존 컴포넌트·네비게이션·저장 계약에 연결 | 변경 파일과 실제 동작 경로 |
| 표적 검증 | 주요 흐름과 실패·재개·화면 제약 중 해당 사항 확인 | 무엇을 자동/직접 확인했는지 |

완료를 선언할 때는 '기능 존재', '자동 테스트 통과', '실제 화면에서 이해 가능', '실기기에서 사용 가능'을 구분한다. 자동 테스트는 휴먼팩터나 미학적 품질을 모두 증명하지 못한다. 반대로 실기기 없이 모든 앱의 UX가 실패했다고 단정할 필요도 없다. 확인하지 못한 부분은 한계로 명시한다.

## 6. 사용자 경험을 망가뜨리는 흔한 AI 개발 패턴

| 부적절한 접근 | 더 적절한 판단 |
|---|---|
| 빈 공간이 보인다고 입력창·카드를 늘려 화면을 채운다 | 실제 콘텐츠의 적정 크기를 유지하고 화면 전체의 균형, 시선 이동, 아래쪽 핵심 행동의 위치를 조정한다 |
| 주요 행동과 보조 도구를 구현 순서대로 쌓는다 | 사용 맥락과 행동 중요도를 기준으로 시각적 집단과 강약을 정한다 |
| 기능을 구현한 즉시 UX가 완료되었다고 본다 | 사람이 발견·이해·조작·취소·복귀할 수 있는지 별도로 살핀다 |
| 강조하기 위해 모든 항목을 카드·그라데이션·큰 제목으로 만든다 | 진짜 중요한 요소만 대비를 주고 나머지는 조용하게 배치한다 |
| '친절함'을 위해 감성 문구·설명을 반복한다 | 사용 시점에 필요한 문장만 짧고 명확하게 제공한다 |
| 빈 상태·에러·긴 텍스트·키보드를 디자인 범위 밖으로 본다 | 실제 조건의 표현과 조작 상태를 설계에 포함한다 |
| 문제가 발생하면 증상 화면만 손본다 | 원인이 된 상태·데이터·비동기 경로와 사용자 시나리오를 검증한다 |
| 테스트·빌드가 성공했으니 사람에게 사용 가능하다고 선언한다 | 자동 검증 증거와 실제 UX·기기 확인 범위를 구분한다 |

## 7. 변경 금지·과잉 설계 방지

이 문서는 모든 앱에 동일한 화면 구조·컴포넌트·애니메이션·버튼 위치를 요구하지 않는다. UX 품질을 이유로 정상 기능을 재설계하거나 브랜드를 바꾸거나 의존성을 추가하지 않는다. 사용자 요청이 분석만이라면 변경하지 않는다. 단순 변경에 반복적인 고비용 E2E, 수십 장의 시안, 전체 리브랜딩을 요구하지 않는다. 앱의 목적과 위험에 맞는 최소 충분한 설계·검증을 선택한다.

세부적인 색·간격·타이포그래피는 `UI_DESIGN_GUIDE.md`, 프로젝트별 이용자·상황·금지사항은 `UX_PROJECT_BRIEF.md`에서 다룬다.
