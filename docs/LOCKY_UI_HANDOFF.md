# Locky UI 개편 인수인계와 단계별 개발 계약

대상은 charmjh7-lab/Locky의 실제 main 코드다. 목표는 기존 기능을 유지하면서 사용 편의·시각적 위계·슬롭 없는 언어·Android 안정성을 함께 개선하는 것이다. 이 문서는 실행 순서와 검증 방식을 정할 뿐, 모든 단계를 한 작업에서 즉시 수행할 권한을 부여하지 않는다. 제품 의도는 docs/PRODUCT_PRINCIPLES.md, docs/UX_PROJECT_BRIEF.md 및 루트 DESIGN.md, 작업 범위 우선순위는 docs/CHANGE_SCOPE_POLICY.md에서 확인한다.

## 준비: 현재 구현과 설계 기준 비교

별도 개발 창은 최신 main SHA와 관련 UI/네이티브 파일, tests, GitHub Actions를 확인한다. 실제 사용 흐름을 기준으로 '코드에 구현됨 / 사용자 의도와 차이 있음 / 기기에서 미검증 / 이번 범위 밖'을 구별한다. 과거 완료 보고·가짜 HTML 시안·시뮬레이션 화면을 현재 제품의 정확한 모습이라고 가정하지 않는다. 이미 존재하는 일반 UX 문서를 다시 여러 벌 복사하지 않는다.

이 준비 단계에서는 UI·데이터·설정·권한을 변경하지 않는다. 기록해야 할 근거는 시작 오버레이와 직접 실행 홈, 관리 앱 진입·연장·차단, 타이머, 설정, 메모/체크, 브리핑, ChatGPT, 외부 사전 왕복 및 복귀 경로다. 같은 상태·화면 크기에서 실제 앱의 화면과 코드를 비교할 기준을 남긴다.

## 첫 구현 범위: 시작 화면의 구성과 위계

기존 상단 도구(메모/ChatGPT와 사전), 하단 목적 선택, 가장 아래 큰 붉은 '그냥 끄기'를 유지한다. 먼저 레이아웃과 타이포그래피, 영역 대비, 여백의 관계를 설계한다. 색상·모서리·카드 교체만으로 끝내지 않는다. 이미 해결된 중앙 빈 공간과 도구창 과대 확대 문제를 재발시키지 않는다. 위계는 화면 상단 우선 배치를 뜻하지 않는다. 작은 화면에서 종료 버튼과 목적 선택이 누를 수 있는지, 프리셋이 많아도 전체 보기가 되는지 확인한다.

실제 Locky 소스에 국소적으로 적용한 후 동일 상태의 수정 전후 화면 증거를 제출한다. 사용자가 디자인을 보고 판단할 수 있게 하되 별도 가짜 HTML 프로토타입은 만들지 않는다. 이 범위에서 자동 오버레이와 직접 실행 홈의 역할 차이를 파악하되 무단으로 다른 화면/태스크 정책을 재작성하지 않는다.

## 이후 화면 확장

관리 앱 진입과 연장·완전 차단은 목적 선택, 시간, 중지/연장/차단 상태의 정보 구조를 각각 맞춘다. 직접 실행 홈과 설정은 빠른 편집·관리, 브리핑은 통계의 정확성과 분석의 유용성, 메모와 ChatGPT는 콘텐츠·입력·오류·출처 가독성을 중심으로 시각적 위계를 설계한다. 모든 화면을 같은 카드 템플릿으로 만들지 않는다. 한 단계에서 확정된 결정과 기존 기능을 다음 단계가 임의로 뒤집지 않는다.

라이트·다크 디자인 방향은 A/C를 참고하되 픽셀값과 세부 장식이 확정된 것은 아니다. Android WebView와 네이티브 오버레이/시스템 바의 색상 일치, 큰 글꼴, 폴더블·키보드 대응을 구현 범위에 맞게 진행한다. 디자인 언어는 선택된 실제 화면 결과를 근거로 DESIGN.md에 정리한다.

## 작업 전 합의와 사후 검토

개발 AI는 구현 전에 이번 사용자 목표, 관련된 확정 원칙, 현재 구현과의 차이, 영향을 받을 사용자 흐름과 건드리지 않을 영역을 간결히 식별한다. 설계 대안을 결정하는 것은 개발 AI의 재량이지만 승인되지 않은 배치 변경은 재량이 아니다. 사용자가 지시하지 않은 기능·데이터 변경은 미적용 제안으로 보고한다.

작업 후 실제 commit/diff, 변경 이유, 수행한 표적 테스트, 수정 전후 화면, 사용자 동선과 문구 검토, 미확인 실기기 항목을 전달한다. 독립 검토는 변경 범위, 조작성, 시각적 위계, 슬롭 유무, 실제 동작·회귀를 별도로 확인한다. 실패하거나 마음에 들지 않는 결과는 해당 화면·원인만 수정하고 매 단계의 전체 설계 재검토를 반복하지 않는다. 앱을 설치해 검증해야 하는 작업에서만 사용자가 요청한 Release APK를 기존 서명으로 제공하고, 문서 작업이나 초기 설계 단계에서 APK를 만들지 않는다.

## 핵심 수용 기준의 차이

시각 검토는 '예쁘다'는 자기평가가 아니라 사용자 눈에 들어오는 중심, 영역 간 강약, 기능의 묶임, 문구의 역할, 종료 버튼의 독립성을 확인한다. 사용성 검토는 탭 대상의 실제 위치·크기, 스크롤·키보드·작은 화면, 눌렀을 때 완료/취소/복귀를 확인한다. Android 검토는 Activity/접근성 오버레이·최근 앱 복귀·잠금 해제·외부 사전 왕복 등 관련 플랫폼 동작을 확인한다. 자동 테스트가 통과해도 시각적 완성도와 실기기 성공은 자동 승인되지 않는다.
